# Feature Specification: AI 原生游戏创作平台 MVP

**Feature Branch**: `001-ai-game-creation-platform`

**Created**: 2026-08-30

**Status**: Conditional Implementation Go — Commercial Unity Gate Pending

**Input**: 面向完全没有编程经验的普通用户，通过自然语言完成“想法 → 可试玩 2D Web 游戏 → 对话式持续修改”的 AI 原生游戏创作平台；MVP 以猫咪跑酷垂直切片验证生成、运行、自动游玩、评估、自修复、浏览器试玩与局部修改闭环。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从一句话获得可试玩游戏 (Priority: P1)

作为完全不会编程的创作者，我希望只描述一个简单的 2D 游戏想法，就能看到系统理解需求、推进创建过程，并最终直接试玩游戏，而无需接触代码、项目文件或开发工具。

**Why this priority**: 这是产品唯一必须首先证明的核心价值；如果“自然语言到可试玩游戏”无法稳定闭环，其余能力没有独立商业价值。

**Independent Test**: 新用户输入“做一个可以跳跃、躲避障碍物、收集金币的猫咪跑酷游戏”，在不提供任何技术信息且不查看代码的前提下，获得可启动、可操作、包含移动/跳跃/金币/障碍/死亡与重开规则的浏览器试玩版本。

**Acceptance Scenarios**:

1. **Given** 用户创建空白项目，**When** 用户提交猫咪跑酷描述，**Then** 系统先形成可审计的结构化游戏规格与执行计划，再开始创建游戏。
2. **Given** 游戏正在创建，**When** 系统完成或切换任务，**Then** 用户看到以游戏能力命名的进度、当前状态和可理解的失败信息，而不是代码或工具调用细节。
3. **Given** 首次生成完成，**When** 系统运行并验证游戏，**Then** 移动、跳跃、金币收集、障碍碰撞、死亡和重新开始均有明确通过或失败结论。
4. **Given** 逻辑验证通过，**When** 用户打开预览，**Then** 用户可直接在浏览器中启动并操作游戏，无需下载项目或安装开发工具。

---

### User Story 2 - 系统自动发现并修复逻辑问题 (Priority: P2)

作为普通创作者，我希望系统在交付前真正运行和游玩游戏，自动发现会阻断基本玩法的问题并尝试修复，避免收到“能构建但不能玩”的结果。

**Why this priority**: 自动验证是 AI 游戏创作区别于一次性代码生成的关键质量保障，也是端到端成功率的主要来源。

**Independent Test**: 向一个存在“金币无法拾取”缺陷的基准项目发起验证，系统能执行相关动作、读取游戏状态、输出结构化问题、限定次数地修复并重新验证；若未修好则明确告知剩余问题。

**Acceptance Scenarios**:

1. **Given** 游戏可以启动，**When** 自动游玩开始，**Then** 系统执行与游戏类型匹配的输入序列并同时采集画面、运行错误和关键实体状态。
2. **Given** 验证发现逻辑错误，**When** 错误可在剩余修复预算内处理，**Then** 系统定位受影响能力、进行局部修复并只重跑相关检查及必要回归检查。
3. **Given** 连续 5 次修复仍未通过，**When** 循环终止，**Then** 系统保留最后一个可运行版本，并向用户说明已完成能力、未解决问题及其影响，绝不宣称全部成功。

---

### User Story 3 - 用自然语言持续修改现有游戏 (Priority: P3)

作为创作者，我希望试玩后直接说“猫跳得太高了”或“把金币分数改为 20”，系统就能理解这是对当前游戏已支持能力的修改，只变更相关参数或配置、验证影响并刷新预览。

**Why this priority**: 对话式迭代把一次性生成变成持续创作体验，是产品留存和可用性的核心。

**Independent Test**: 对已通过验证的跑酷游戏提交“猫跳得太高了”，系统更新持久化游戏规格中的跳跃参数，生成局部变更任务，完成针对性验证并发布新预览，同时保持金币、障碍和死亡规则不变。

**Acceptance Scenarios**:

1. **Given** 项目已有可试玩版本，**When** 用户提出局部数值修改，**Then** 系统先更新游戏规格，再定位受影响能力并生成局部任务，不重建整个项目。
2. **Given** 修改涉及多个已支持的跑酷能力或配置，**When** 系统识别依赖关系，**Then** 系统扩展局部任务计划、验证变更能力，并对受影响的既有能力执行回归检查。
3. **Given** 用户请求超出 MVP 能力边界，**When** 系统无法可靠完成，**Then** 系统解释限制并保持当前可玩版本不受损。

---

### User Story 4 - 查看版本并撤销修改 (Priority: P4)

作为创作者，我希望每次重大修改都保留可理解的版本，以便在结果不满意时用自然语言撤销并恢复可试玩版本。

**Why this priority**: AI 修改具有不确定性，可恢复版本能降低用户试错成本并保护已有成果。

**Independent Test**: 在 v1 基础移动、v2 增加金币、v3 调整跳跃三次重大修改后，用户请求“撤销刚刚的修改”，系统恢复 v2 的规格、项目状态和对应预览。

**Acceptance Scenarios**:

1. **Given** 一次重大修改准备执行，**When** 当前版本可运行，**Then** 系统在修改前创建包含变更摘要的检查点。
2. **Given** 用户请求撤销，**When** 目标检查点有效，**Then** 系统恢复该版本并完成最小健康验证后更新预览。
3. **Given** 回滚失败或目标版本损坏，**When** 系统无法安全恢复，**Then** 系统不覆盖当前可用版本，并给出明确错误状态。

---

### User Story 5 - 管理素材而不处理工程文件 (Priority: P5)

作为创作者，我希望使用内置素材、占位图形或自己上传的图片，并能理解素材来源和用途，而不需要手动处理游戏目录。

**Why this priority**: 视觉反馈对游戏创作必要，但 MVP 应控制素材复杂度，优先保证玩法闭环。

**Independent Test**: 用户上传一张猫咪图片并要求替换角色，系统校验文件、登记来源与许可信息、替换角色素材、验证游戏仍可运行，并刷新预览。

**Acceptance Scenarios**:

1. **Given** 用户未提供素材，**When** 游戏需要视觉元素，**Then** 系统使用许可清晰的内置素材、简单形状或占位资源完成可玩版本。
2. **Given** 用户上传受支持图片，**When** 文件通过安全与格式校验，**Then** 系统记录来源、许可、元数据和使用位置后应用到项目。
3. **Given** 素材不受支持、损坏或许可信息不足，**When** 导入失败，**Then** 系统保留现有素材并给出可操作提示。

---

### User Story 6 - 多用户安全运行与开发者排障 (Priority: P6)

作为平台运营者，我希望不同用户项目严格隔离，长时间创建任务可恢复、取消和追踪，并能从后台定位模型、工具、任务、游玩和修复失败的原因。

**Why this priority**: 这是从单机技术验证走向可供真实用户使用的服务所必需的安全与运营能力。

**Independent Test**: 两个用户并发创建游戏时，验证彼此无法读取或修改对方文件、构建和日志；中断其中一个会话后能够从持久状态恢复，并通过统一事件记录复盘全过程。

**Acceptance Scenarios**:

1. **Given** 多个项目并发运行，**When** 任一项目执行生成或游玩任务，**Then** 其文件、进程、网络、资源和凭据访问均受项目边界限制。
2. **Given** 创建任务正在执行，**When** 用户请求暂停，**Then** 系统在当前不可中断操作结束后进入安全暂停状态，持久化恢复点并释放独占执行资源；用户恢复任务或任务意外中断后重启时，系统从该持久状态继续，而不是仅依赖聊天记录重推项目状态。
3. **Given** 任务失败，**When** 开发者查看后台记录，**Then** 能关联查看会话、模型调用、工具调用、任务状态、游戏状态、验证结果、修复原因、耗时、用量和错误。

### Edge Cases

- 用户描述互相冲突、过度宽泛或超出 2D 单机 Web 游戏边界时，系统应指出冲突、缩小为可执行范围，且不静默承诺不支持的能力。
- 用户在生成过程中连续追加或撤回需求时，系统应基于当前任务状态排队、合并或取消变更，避免并发写入破坏项目。
- 模型、创作运行时、游戏工具或导出服务暂时不可用时，任务应进入可恢复状态，并保留最后一个一致的项目版本。
- 游戏能启动但关键玩法不可达时，系统应判定验证失败，而不是把“进程退出码正常”视为成功。
- 自动操作因焦点、帧率或时间抖动失败时，应允许确定性状态检查和有限重试，并区分“测试基础设施失败”与“游戏逻辑失败”。
- 上传素材过大、格式伪装、包含恶意内容或许可证不明确时，应拒绝使用并保持项目状态不变。
- Web 构建产物缺失、缓存过期或加载失败时，应阻止发布失效预览，并回退到上一可用构建。
- 修复引入回归、任务依赖循环或局部修改影响范围超出预期时，应停止继续写入，保留检查点并报告阻塞原因。
- 用户请求撤销到已清理或不可恢复的版本时，应明确说明并提供最近的可恢复版本。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须允许用户仅通过自然语言创建和修改游戏，主流程不得要求用户阅读或编写代码。
- **FR-002**: MVP 必须把可承诺范围限定为单人 2D 浏览器游戏，并以跑酷垂直切片作为首个发布门槛；超范围请求必须明确提示。
- **FR-003**: 系统必须在修改项目实现前生成或更新一份结构化、可校验、持久化且有版本的 Game Spec，作为项目期望状态的权威来源。
- **FR-004**: 系统必须把 Game Spec 转换为带唯一标识、类型、描述、依赖、状态、重试次数、验证方法、关联文件和关联场景的任务图。
- **FR-005**: 任务状态必须至少支持 `pending`、`running`、`blocked`、`failed`、`completed`，且每次状态变化都可追溯。
- **FR-006**: 系统必须向用户展示以玩法能力命名的创建进度、当前活动、完成项、失败项和下一步，不默认暴露终端、文件树、版本控制、工具调用、模型用量或脚本编辑器。
- **FR-007**: 系统必须能够创建一个包含场景、角色、关卡、玩法规则、界面和基础素材的完整可运行项目，而非只输出代码片段。
- **FR-008**: 系统必须优先通过可复用的高层 Game Skill、模板和结构化 Game Tool 完成常见玩法，且记录每次使用的技能与结果。
- **FR-009**: 系统必须在交付前真实启动游戏，并收集脚本错误、运行错误、日志、画面和关键游戏状态。
- **FR-010**: 自动游玩必须支持按下/释放动作、移动、跳跃、射击、点击、等待、重开和采集画面，并能读取玩家位置、生命值、敌人数量、分数、当前场景及与验证相关的实体状态。
- **FR-011**: 评估器必须依据游戏类型和 Game Spec 输出结构化结论，包括总体状态，以及每个问题的唯一标识、严重度、描述、证据和对应需求。
- **FR-012**: 系统必须对可修复失败执行“分析 → 局部修复 → 运行 → 游玩 → 评估”闭环，单次用户请求默认最多 5 次自修复迭代。
- **FR-013**: 达到修复上限后，系统必须停止循环、保留最后一个可运行版本，并诚实报告未解决问题及其影响。
- **FR-014**: 验证通过后，系统必须生成可直接在受支持浏览器中启动的预览，并把预览与不可变构建版本关联。
- **FR-015**: 用户提出修改时，系统必须先更新 Game Spec，再计算影响范围、生成局部任务、执行相关测试和必要回归测试，除非完整重建有明确理由。
- **FR-016**: 每次重大修改前系统必须创建可恢复检查点；用户必须能查看人类可读的版本摘要并撤销到最近的有效版本。
- **FR-017**: 系统必须持久保存 Project、Game Spec、Task Graph、Scenes、Scripts、Assets、Skills Used、Current Build、Test Results、Agent History 和 Version History 的关联状态。
- **FR-018**: Asset Manager 必须统一记录素材标识、类型、路径、来源、许可、元数据和使用位置，并支持内置免费素材、占位资源、简单形状及用户上传图片。
- **FR-019**: 系统必须支持创建会话、运行、安全暂停、恢复、取消、流式进度和状态查询；暂停请求必须在当前不可中断操作完成后持久化恢复点、释放独占执行资源并进入 `paused` 状态，恢复时重新取得所需资源；中断恢复不得依赖重新解析完整聊天历史。
- **FR-020**: 每个用户项目必须在独立执行边界内运行，并限制 CPU、内存、磁盘、时长、网络、进程数和文件访问。
- **FR-021**: 开发者可观察性必须关联记录会话、模型调用、工具调用与结果、任务状态、游戏状态、游玩结果、评估结果、修复原因、用量、延迟和错误，普通用户默认不可见这些内部细节。
- **FR-022**: 项目状态和上层游戏流程必须保持对具体模型、Agent Harness 和游戏运行时实现的可替换性；替换底层实现不得要求迁移 Game Spec 的业务语义。
- **FR-023**: 系统必须对任务、工具和外部依赖失败提供结构化错误、可重试性标记和用户可理解的降级路径。
- **FR-024**: 系统必须拒绝把大型 3D、多人联网、MMO、主机/原生移动发布、游戏社区、商店和复杂 AI 资产生产纳入 MVP 成功判定。
- **FR-025**: 在受控 beta 或商业使用前，项目必须取得适用于云端 Unity Editor、构建执行器、席位和用户生成项目场景的书面许可结论；结论必须指定批准人、适用组织、许可容量、复核日期和 go/no-go 决定，未批准或过期时不得启动超出已确认范围的执行容量。

### Scope Boundaries

**MVP In Scope**:

- 一个稳定的 2D 跑酷基准垂直切片：移动、跳跃、障碍、金币、死亡、重开、自动验证、自修复、Web 预览，以及对这些既有能力的局部参数和配置修改。
- 受控模板、Game Skill 和结构化工具驱动的生成策略，成功率优先于开放式自由度。
- 面向普通用户的聊天、进度、预览、简单素材和版本体验。
- 为后续增加其他 2D 类型预留一致的 Game Spec、Planner、Skill、Tool、Playtest 和 Evaluation 扩展边界。

**Out of Scope for MVP**:

- Godot、Unreal、大型 3D、多人联网、MMO、AAA、主机或原生移动发布。
- 多 Agent 团队、自研基础模型、自研游戏引擎、自研完整通用 Coding Harness 或完整通用游戏编辑器自动化平台。
- 复杂检索增强、游戏社区、商店、Steam 发布、AI 3D 建模，以及完整 AI 音乐/动画/3D 资产生产链。
- 对“是否好玩”的高级平衡性判断；MVP 只保证核心游戏逻辑正确并可操作。
- 通过自然语言增加 Boss、新敌人类型或其他需要新增玩法实现的能力；MVP 对此类请求解释限制并保留当前可玩版本。

### Key Entities

- **User**: 平台使用者；拥有项目、会话、上传素材和可见权限。
- **Project**: 一款持续演化的游戏创作工作区；聚合规格、任务、文件、构建、测试、会话与版本。
- **Game Spec**: 游戏的声明式期望状态；包含元信息、类型、玩家、玩法系统、关卡、资源、界面、胜负条件和验证要求，并独立版本化。
- **Task Graph / Task**: 从规格派生的执行计划及其依赖关系、生命周期、重试和验证信息。
- **Agent Session / Run**: 一次可恢复的用户意图处理与执行过程；关联事件、模型、工具、任务和结果。
- **Game Skill**: 可复用的高层游戏开发能力；声明输入、前置条件、调用的结构化能力、产物和验证方法。
- **Tool Invocation**: 对受控游戏、文件、素材、运行、游玩或导出能力的一次结构化调用及结果。
- **Asset**: 内置、占位或用户上传的游戏资源；记录来源、许可、元数据和使用关系。
- **Playtest Run**: 一次可复现的自动游玩执行；包含动作、时间线、状态样本、画面、日志和环境结果。
- **Evaluation Report / Issue**: 对规格要求的验证结论及带证据的问题集合。
- **Build / Preview**: 与项目版本绑定的不可变游戏产物及其可试玩地址和健康状态。
- **Checkpoint**: 一次重大修改前后的可恢复快照及人类可读变更摘要。
- **Observability Event**: 供开发者关联排障的不可变事件记录。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在固定的猫咪跑酷验收描述上，10 次不复用既有项目文件、规格或构建产物的全新项目运行中，至少 8 次能在 15 分钟内产出可直接试玩且核心规则通过的版本。
- **SC-002**: 新手用户在不查看代码、不安装开发工具且不接受人工技术协助的情况下，至少 85% 能完成“提交描述 → 打开预览 → 操作角色”的主任务。
- **SC-003**: 在至少 60 个预先冻结的基准检查样本上，移动、跳跃、障碍、金币、死亡和重开每类至少包含 10 个通过或失败样本；系统在不超过 5 次自修复后至少 90% 给出与人工参考结论一致的通过/失败判断。人工参考结论由两名复核者独立判断，分歧由第三名复核者仲裁后冻结。
- **SC-004**: 对“猫跳得太高了”这类局部参数修改，至少 90% 在 5 分钟内更新预览，且未受影响的基准玩法回归通过率不低于 95%。
- **SC-005**: 100% 达到修复上限的运行都明确报告未解决问题，不把部分成功呈现为全部完成。
- **SC-006**: 用户可在 60 秒内从最近一个有效检查点恢复项目并启动对应预览。
- **SC-007**: 主流程中 100% 的进度提示使用用户可理解的游戏能力与结果描述，默认界面不要求用户接触代码、文件、终端或版本控制概念。
- **SC-008**: 在并发隔离验收中，项目间文件、进程、构建、日志和凭据的未授权交叉访问为 0。
- **SC-009**: 至少 95% 的失败运行能在单一关联链路中找到任务、工具、运行状态、评估证据和最终用户提示。
- **SC-010**: Web 预览在目标桌面浏览器验收矩阵中至少 95% 能在 10 秒内进入可操作状态，并且旧缓存不会覆盖用户选定的最新构建。

## Assumptions

- 第一版发布门槛只承诺一个高成功率的 2D 跑酷垂直切片；Platformer、Shooter、Survivor-like、Tower Defense 等其他 2D 类型按同一扩展架构逐步加入，不纳入首个 MVP 验收。
- 新增 Boss、新敌人类型或其他新增玩法实现不属于首个 MVP 的自然语言修改承诺；首版只保证跑酷垂直切片中既有能力的参数和配置调整。
- 第一版只实现一个游戏引擎适配器；Game Spec、Planner、Skills、Playtest 和 Evaluation 保持引擎无关，增加第二引擎不属于 MVP。
- 用户具有稳定网络和支持 Web 图形能力的现代桌面浏览器；移动端浏览器体验不是首个发布门槛。
- 平台可使用一个能力足够强的默认模型完成规划、编码、视觉与评估，但业务状态允许后续按角色切换模型。
- 高风险或未知许可的上传素材不进入可发布构建；缺少合适素材时允许使用占位图形保障玩法验证。
- 自动评估优先使用可重复的结构化游戏状态证据，画面理解用于补充视觉和交互判断。
- 每次用户请求默认最多进行 5 次自修复；管理员可为离线基准测试配置不同预算，但不改变用户承诺。
- 初始服务容量以小规模受控测试为目标，先验证端到端成功率，再扩展到通用多类型和大规模并发。
- 项目宪法已于 2026-08-30 获项目负责人批准用于受控实现与确定性 fixture 验收；Unity 云端 SaaS、商业 beta 与并发容量仍须遵循 ADR-0001 的外部书面许可 Gate。
- Unity 云端 SaaS 与并发执行容量必须以书面许可结论为前提；该结论属于外部依赖，不由本文替代法律或商务确认。

## 优先处理的问题

### P1：新玩法代码难以持续保留

每次创建执行器都会同步模板；脚本、美术、Editor、Tests 和 Plugins 使用强制覆盖复制。若 Agent 修改了项目中与模板同名的文件，下一轮同步可能覆盖这些修改。额外新建的文件不一定受影响，当前逻辑并非删除整个目录。

应区分模板维护的基础代码与项目生成代码，为模板更新引入版本和迁移机制，并在项目版本中保存脚本、场景、资源及配置。验收必须包含“新增机制 → 修改它 → 再制作 → 恢复旧版”后的行为一致性。

证据：[同步实现](/D:/Desktop/gamerhub/apps/local-dev/src/real-unity.ts:558)。

### P1：规划器与 Agent 的正常执行仍受固定任务链限制

Planner 先检查已注册运行时，再从固定任务链中选择执行步骤。Pi 的工作区读取、搜索、编辑与 CLI 工具主要在 repair 阶段开放，正常执行以调用已有业务动作为主。因此，接入真实 Pi 循环并不等于已经能主动实现任意新机制。

建议增加明确的机制开发阶段：识别已有能力和缺口，生成具体实现任务，在项目工作区编写代码与场景内容，通过编译、机制测试和实际操作验收后再交付。保持现有任务授权和工具边界，让开发阶段成为正式工作流。

证据：[任务规划](/D:/Desktop/gamerhub/packages/game-planner/src/planner.ts:230)、[工具阶段](/D:/Desktop/gamerhub/apps/platform-fastapi/gamerhub_api/pi/tools.py:14)。

### P1：制作说明与实际参数需要严格对应

本轮复现并修复：制作说明允许自定义 system_id，但 Unity 导入曾使用固定 ID 查找配置。将系统 ID 改名后，已确认的伤害 7、敌人生命 9、升级经验 5、生成间隔 3 会回退为默认的 1、2、3、2。现在按启用系统的 type 读取，并拒绝当前运行时无法区分的重复启用系统类型。

后续应为每项机制定义配置字段、范围、映射和行为验收；不能识别的配置应明确报错。当前战斗和经验检查较具体，其他系统仍需补齐逐字段约束，胜负条件也需要逐项核对执行语义。

证据：[配置导入](/D:/Desktop/gamerhub/apps/local-dev/src/real-unity.ts:68)、[新增回归测试](/D:/Desktop/gamerhub/tests/unit/gameplay-capability-audit.test.ts:9)。

### P2：现有原型的玩法深度与边界行为不足

竞技场使用最近目标直接扣血，幸存者与射击主要由是否自动攻击区分；升级选择也较固定。应先补充瞄准、投射物、攻击反馈、敌人行为和成长组合，使两类玩法形成不同体验。

点击成长存在时间边界问题：Step 先计算整个 delta 的收益，再判断超时。例如初始自动收益 1、目标 50、时限 30 秒，传入 60 秒的 Step 会先获得 60 并胜利。应只结算剩余有效时间，再按明确规则判定截止时刻的胜负。本轮仅完成代码推导，尚未修改此 Unity 行为或运行其专项测试。

证据：[竞技场逻辑](/D:/Desktop/gamerhub/unity/Templates/Runner/Assets/Game/Scripts/ArenaSimulation.cs:45)、[点击成长 Step](/D:/Desktop/gamerhub/unity/Templates/Runner/Assets/Game/Scripts/ClickerSimulation.cs:21)。

### P2：名称、中文和操作体验需要一致

跑酷页面仍有固定英文标题和说明；通用画布在字体不包含标题字符或标题过长时使用备用标题。字体是子集，无法覆盖任意中文名称。跑酷触屏主要提供跳跃，缺少与键盘相当的左右操作。需要统一使用项目名称、完善字体覆盖及换行、补齐暂停和触屏操作，并测试窄屏布局。

证据：[跑酷界面](/D:/Desktop/gamerhub/unity/Templates/Runner/Assets/Game/Scripts/RunnerGameManager.cs:72)、[标题处理](/D:/Desktop/gamerhub/unity/Templates/Runner/Assets/Game/Scripts/GameCanvas.cs:12)、[字体说明](/D:/Desktop/gamerhub/unity/Templates/Runner/Assets/Resources/Art/GameFont-NOTICE.txt)。

## 扩展顺序建议

以下是设计建议，尚未实施。

1. **先打通扩展与保留能力**：项目代码归属、模板迁移、机制开发阶段、严格配置契约、能力缺口展示。
2. **完善现有四类**：补齐实际射击机制、成长组合、游戏状态和边界测试、中文与移动端操作。
3. **补齐较小的完整玩法**：飞行躲避、打砖块，用新机制开发流程证明可以新增而非仅调整现有参数。
4. **扩展平台跳跃和塔防**：分别建设关卡/碰撞/检查点，以及路线/波次/建造/寻路等能力。
5. **明确解谜和 RPG 的子类型**：先选择具体规则，例如推箱子或对话分支；“解谜”“RPG”本身不足以定义验收范围。
6. **另行规划 3D、联机和开放世界**：需要各自的场景、控制、资源、同步和性能方案，当前目录不能作为已有支持的依据。

长期应按机制登记输入方式、状态、配置、资源接口和测试要求，让类型成为预设组合。例如移动、碰撞、投射物、波次、背包、对话和存档可以组合复用。只有配置了接口和组合约束，新增模块才能稳定协作。

每个机制都应有可观测的验收目标：瞄准方向是否改变命中对象、超时后是否停止收益、暂停时状态是否冻结、存档恢复后数值是否一致。默认测试通过或测试数量达到门槛，不能单独证明玩法完整。

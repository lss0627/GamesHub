## 玩法覆盖

| 类型 | 已实现的具体玩法 | 当前范围 |
| --- | --- | --- |
| 跑酷 | 左右移动、跳跃、金币、障碍、倒计时、暂停、重开和触屏按钮 | 单场景自动横向移动 |
| 幸存者 | 自动弹道攻击、追踪/快速/坦克敌人、经验、伤害/攻速/回血/多重攻击升级 | 有界竞技场 |
| 俯视射击 | 鼠标或触屏瞄准、真实弹道、主动射击、经验与升级 | 共用竞技场，不含装填与武器仓库 |
| 点击成长 | 点击与自动收益、购买升级、限时目标、暂停 | 单资源经济，不含离线存档 |
| 飞行躲避 | 飞跃、重力、随机门洞、计分、8道门通关 | 单关卡；碰撞或越界失败 |
| 打砖块 | 挡板移动、发球、反弹、24块砖、漏球扣生命 | 单块砖一击消除 |
| 平台跳跃 | 自由横向移动、跳跃、深坑、金币、两个检查点与终点 | 一条固定地图 |
| 塔防 | 6个建造位、固定路线、建塔与三级升级、击杀收益、5波敌人、基地生命 | 一种基础防御塔 |
| 解谜 | 8×6推箱子关卡、3个箱子、撤销、超时和重开 | 当前具体实现为推箱子 |
| 对话冒险 | 营地/森林/河边选择、钥匙状态、成功与失败结局 | 固定星灯故事，不含完整RPG战斗 |

`custom` 保留为创意入口。新增机制可以依托这些运行时进入正式开发；全新运行时、3D、联机和开放世界仍需独立实现。目录中的类型名称不意味着已覆盖该类型的全部商业游戏机制。

## 开发与项目保留

- 制作说明可包含明确的机制描述与2—6条行为验收。Planner据此插入正式开发任务，标出当前玩法入口文件。
- Python控制开发阶段的文件和CLI工具，官方Pi负责模型与工具循环。Agent可以先读代码、编写机制与测试，再执行编译和专项PlayMode验证；既有验收文件保持只读。
- 新机制必须至少通过两项真实行为检查，随后通过原有玩法检查和网页构建，才能发布。创意要求不会仅因写入说明就被标记为已经实现。
- 模板使用逐文件哈希基线。未修改的模板文件可以升级；项目修改、新机制和主动删除的文件得到保留。旧内容保存在本地备份中。
- 源码快照包含Assets、Packages与ProjectSettings，并校验所有文件的哈希。发布版本与源码映射不可覆盖。恢复先应用源码，再标记检查点完成；现有网页构建保持独立。

对于没有旧模板基线的历史工程，系统保留有差异的代码，避免猜测文件归属。此类差异需要后续合并验证，不能保证自动获得新版模板的全部改进。已经发布的旧游戏没有被批量替换。

## 参数与上下文

配置校验和Unity参数映射共用机制描述，避免自定义系统ID导致参数退回默认值。重复系统、未知参数、矛盾胜负规则，以及无法完成固定关卡的部分参数组合，会在制作前给出缺口。旧版三项升级仍按三项执行，新版可确认第四项多重攻击。

点击收益只计算有效游戏时间，修复超时帧多发资源和NaN时间问题。项目名称得到保留；完整中文字体取代原来的少量字符子集。

设计讨论保留48,000字节预算；代码执行采用96,000字节预算，并为输出留出余量。压缩以完整的消息和工具批次为单位，保留已确认说明、任务、用户记忆、近期工具结果和可继续读取的源码片段。原始记录与提供方要求的字段不做截断修改。

真实开发检查曾遇到55,997字节的单批次超限。回放已证实可完整归档该批次；后续扩大代码阶段预算并提供入口文件，解决频繁重新读取的原因。所有失败与修正均保留在验收记录中。

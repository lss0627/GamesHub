# 项目逻辑审查与优化：第二轮

本轮承接第一轮报告，完成发布一致性和多 Worker 项目互斥修复。代码已写入工作区；未部署到生产，也未修改原开发数据库。

## 修复结果

| 问题 | 修改后的行为 |
| --- | --- |
| 历史数据存在同项目多个排队 Run，不同 Worker 可同时领取 | PostgreSQL 按 Project → Run 顺序加锁，使用 SKIP LOCKED；有效租约或暂停任务阻止同项目其他任务领取，不同项目仍可并行。内存实现遵守相同规则。 |
| 预览和版本提前切换，Run 随后取消或写入失败造成不一致 | 新预览先保存为 prepared；PostgreSQL 在一个事务中校验租约、任务/项目/构建/checkpoint 归属，再激活版本和预览、更新项目指针、完成 Run、写入 RunEvent/Outbox 并释放租约。创建、修改和恢复共用 Worker 最终提交入口。 |
| 全局构建哈希去重可能覆盖其他项目或任务的构建记录 | 新增 009_build_identity.sql，把幂等键限定为项目、checkpoint、spec 和内容哈希；预览准备支持按 sourceRunId 限定构建查询。相同文件内容可保留各自归属。 |
| 创建流程传给发布服务的哈希来自证据 JSON，与实际构建不一致 | 优先使用 build evidence 中的实际 contentHash；无哈希的兼容路径保留原回退计算。 |
| Agent 最终诊断先于 Run 完成，诊断失败可能阻止业务收尾 | 先持久化成功或失败，再尝试诊断终结；诊断失败不覆盖业务结果。发生提交响应不确定时，Worker 读取到已成功的 Run 会返回成功。 |
| 迁移使用 pool.query，BEGIN 和后续语句可能落到不同连接 | 固定一个数据库连接执行迁移事务，并使用会话 advisory lock 串行化多个启动进程；连接与锁在 finally 中释放。 |

发布事务在最后一次写入时再次用数据库 clock_timestamp() 校验租约。事务内下游操作导致租约过期时，版本和预览等写入会整体回滚。

## 使用

现有环境启用本轮 Worker 代码前，应先按原部署流程执行 `pnpm db:migrate`，应用新增的 **009_build_identity.sql**。`pnpm dev` 已在启动步骤中包含迁移。此轮验证没有把迁移应用到原开发库或生产库。

复现 PostgreSQL 发布检查：创建一个全新的空数据库，名称必须匹配 `gamerhub_logic_audit_[a-z0-9_]+`，设置 `GAMERHUB_AUDIT_DATABASE_URL` 后运行 `pnpm exec tsx scripts/audit-publication.ts`。脚本会执行全部迁移和测试，只能用于一次性隔离数据库。

## 仍未覆盖的边界

1. 原子提交保证适用于 PostgreSQL 内部状态。外部 publisher 必须只准备不可变构建，业务的当前预览指针由本事务提交；已经上传的不可变文件可能在失败后残留，外部服务若自行切换域名或路由仍需单独改造。
2. 内存/JSON 开发路径仍是原有版本服务与 Run 分步保存，不提供跨存储事务保证。
3. 本轮项目锁只保护任务领取和数据库发布。失联 Worker 已经发出的 Unity 操作仍需要执行器或工作区层面的 fencing/强制终止；未验证多机网络分区。
4. 原有历史并发任务没有被批量删除或改写；它们会在领取时按项目串行执行。暂停任务仍需恢复或取消。
5. Worker 发布集成检查使用确定性的模拟引擎输出，未调用付费模型、真实 Unity 构建或外部生产发布服务。既有 3 个环境门禁仍跳过。
6. 真实多租户登录、事件与列表分页、完整契约生成器以及 Unity 玩法细节仍是第一轮报告中列出的后续工作。
